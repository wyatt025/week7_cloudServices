    Documentation:
        Why did OpenTofu react differently to the deleted rule and to the added rule? Think about what OpenTofu keeps track of in its state file
            The deleted HTTP rule was declared in the configuration and recorded in OpenTofu's state. 
            During refresh, OpenTofu found that the real rule was missing, so it planned to create it again. 
            The rule I added manually was not declared in the configuration or recorded in state, so OpenTofu did not treat it as a resource it needed to remove.
            
        What does this tell you about making manual changes in an environment that is managed with IaC?
            Changes to resources managed by IaC should be made in the configuration and applied through OpenTofu. 
            Manual changes can create drift; extra resources that are not managed may be left behind because OpenTofu does not necessarily know they should be removed.

    Documentation:
        Compare the actual destroy order with your prediction. What determined it?
            My prediction that the port would be destroyed before the VM was incorrect. 
            OpenTofu began destroying the floating IP, security-group rules, and VM in parallel. 
            After the VM finished, it destroyed the key pair and port; the security group was destroyed last. 
            The order came from the dependency graph: dependent resources must be removed before the resources they rely on, while independent resources can be destroyed in parallel.
        
        why did the project network survive the destroy?
            The project network is declared as a data source, not a resource managed by this configuration. 
            OpenTofu looks it up so the VM can use it, but it does not own or destroy that existing cPouta network.
        
        Why does a changing IP address matter less when you have an output for it — and what would you need if the address had to stay the same?
            The `web_public_ip` and `web_url` outputs show the current address after each apply, so I can find the server even if its address changes. 
            The floating IP is allocated dynamically from the `public` pool, so destroying and recreating it does not guarantee the same address. 
            To keep a stable address, I would need to reserve a specific floating IP and preserve that allocation instead of destroying it.
